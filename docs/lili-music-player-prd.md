# lili 音乐播放器重构 PRD

> 文档版本：v1.0  
> 日期：2026-09-21  
> 产品范围：基于现有 Bilibili 接口、本地能力与 Electron 能力进行信息架构和体验重构，不新增后端服务依赖。

## 1. 文档目的

本文档用于指导 lili 从“包含播放器的 B 站内容工具”重构为“以 B 站音乐内容为来源的桌面音乐播放器”。

本轮重构重点是：

1. 完整盘点当前已经实现并可调用的能力。
2. 参考成熟桌面音乐播放器的通用产品结构，重新组织功能优先级。
3. 删除重复、低价值或破坏音乐主流程的入口。
4. 保留底层接口和业务能力，不提出依赖新曲库、推荐算法、评论系统或云同步后台的功能。
5. 形成后续 UI 设计、技术拆分和验收的统一依据。

## 2. 产品定位

### 2.1 一句话定位

**lili 是一款以 Bilibili 音乐视频、音频和用户收藏为内容来源，兼顾本地音乐与高品质下载的跨平台桌面音乐播放器。**

### 2.2 核心用户

- 经常在 Bilibili 收听音乐、Live、翻唱、演奏、鬼畜音乐或音乐合集的用户。
- 已经积累大量 Bilibili 收藏夹，希望以音乐播放器方式管理和收听的用户。
- 希望从 Bilibili 视频中提取高品质音频、管理本地文件的桌面用户。
- 需要播放队列、歌词、倍速、全屏播放和迷你播放器等完整播放体验的用户。

### 2.3 核心价值

- 把 Bilibili 的视频/音频内容转化成稳定、连续、低干扰的听歌体验。
- 复用用户已有收藏、关注、稍后再看和历史数据，降低重新整理音乐库的成本。
- 同时管理在线播放、本地音乐和下载内容。

### 2.4 产品原则

1. **播放优先**：任何页面都应方便开始播放、加入下一首或加入队列。
2. **音乐语义优先**：界面表达使用歌曲、曲目、播放列表、音乐库，而不是视频信息流术语。
3. **能力真实**：只展示现有服务能稳定支持的内容与操作。
4. **B 站能力下沉**：关注、动态、UP 主空间等能力作为内容发现辅助，不占据核心播放路径。
5. **桌面效率**：强调列表密度、快捷键、右键菜单、拖拽、批量操作和稳定窗口布局。

## 3. 对标产品启示

本 PRD 不复制网易云音乐或 QQ 音乐的具体功能，只参考它们在成熟音乐产品中形成的共同结构。

根据官方产品资料，网易云音乐 Mac 端强调曲库、个性推荐和歌单；QQ 音乐 Mac 端强调曲库、无损音质、歌词、下载、本地音乐，以及可定制的左侧导航。这些产品的共同点是：**发现内容、个人音乐库、持续播放和当前播放详情构成主干，社交、视频和扩展内容位于第二层。**

参考资料：

- [网易云音乐 Mac App Store 页面](https://apps.apple.com/cn/app/%E7%BD%91%E6%98%93%E4%BA%91%E9%9F%B3%E4%B9%90/id944848654?mt=12)
- [QQ 音乐 Mac App Store 页面](https://apps.apple.com/cn/app/qq%E9%9F%B3%E4%B9%90-%E5%90%AC%E6%88%91%E6%83%B3%E5%90%AC/id595615424?mt=12)
- [腾讯音乐业务介绍](https://www.tencentmusic.com/zh-cn/business.html)

对 lili 有效的借鉴：

- 一级导航数量少而稳定。
- 首页负责“快速开始听”，不是展示全部功能。
- 收藏夹以播放列表形式组织。
- 播放栏始终可见，播放详情是独立沉浸层。
- 本地音乐和下载属于个人音乐库。
- 搜索结果按内容类型组织，但首要结果必须能直接播放。

不适合直接引入的能力：

- 个性化推荐、每日私人歌单、私人 FM。
- 正版歌曲、专辑、歌手曲库体系。
- 音乐评论、好友私信、一起听。
- 会员、付费专辑、数字专辑。
- 听歌识曲、K 歌、直播、电台、播客。
- 云端歌单同步和跨设备播放进度同步。
- 专业音效或服务端音频处理。

上述能力需要 lili 当前不具备的内容、算法、版权或后端服务，因此不进入本期产品范围。

## 5. 当前产品主要问题

### 5.1 信息架构问题

- 推荐、关注、稍后再看、历史、本地音乐和下载都以相同权重出现在一级导航。
- 用户关注、动态、UP 主空间等能力强化了“B站客户端”感，而不是“音乐播放器”感。
- 收藏夹、合集、系列在数据层定义不同，但用户的音乐心智都是“播放列表”。
- 核心播放能力分散在底栏、抽屉、全屏页和多个内容菜单中，缺少一致的操作优先级。

### 5.2 语义问题

- “视频”“UP 主”“分P”等词汇大量出现在音乐主流程。
- 搜索仅支持视频和用户，却容易让用户误以为是完整音乐曲库搜索。
- Bilibili 历史与播放器历史的语义容易混淆。
- 视频下载与音频下载权重接近，弱化了音乐产品定位。

### 5.3 功能重复与复杂度

- 列表、网格、紧凑三种全局模式增加页面适配成本。
- 颜色、背景、圆角、字体和各播放器颜色设置过于分散。
- 收藏夹、系列、合集分别存在页面逻辑，但大量交互相同。
- 页面内播放、队列、收藏和下载菜单存在重复实现。

## 6. 新产品信息架构

### 6.1 一级导航

```text
发现音乐

我的音乐
├── 我的收藏
├── 稍后播放
├── 本地音乐
└── 下载管理

我的播放列表
├── 默认收藏夹
├── 用户自建收藏夹…
└── 收藏的播放列表（折叠）
```

固定在页面框架中的能力：

- 全局搜索。
- 用户账户。
- 设置。
- 底部播放器。
- 播放队列。
- 当前播放详情。

不再作为一级导航的能力：

- 我的关注。
- 用户动态。
- 历史记录。
- 创作者空间。

入口调整：

- “我的关注”进入账户菜单或“发现音乐”辅助入口。
- “关注动态”进入关注页内部，不单独占用导航。

## 7. 功能重组决策

### 7.1 保留并前置

- 推荐音乐、流行榜、新歌速递。
- 播放、队列、播放模式、进度、音量。
- 收藏夹/播放列表。
- 本地音乐。
- 音频下载和下载管理。
- 歌词与播放详情。
- 迷你播放器和快捷键。

### 7.2 合并

- 收藏夹、合集、系列：统一为“播放列表详情”页面模板，数据类型不同但界面结构一致。
- 音乐、流行、鬼畜、新歌：统一进“发现音乐”，不再作为相互割裂的模块。
- 关注列表和关注动态：统一为“我的关注”页面的两个 Tab。
- 一般显示密度：以标准列表为默认；网格仅用于适合封面的内容；紧凑样式成为列表密度设置。
- 全屏播放器设置与常规播放设置：统一入口，播放详情中只保留快速开关。

### 7.3 下沉

- 视频下载。
- 点赞、一键三连。
- 打开 Bilibili 原页面。
- 关注分组管理。
- 用户动态。
- UP 主完整空间数据。
- Bilibili 历史。
- 代理、FFmpeg、自定义色值等高级设置。

### 7.4 从主产品表达中删除

- 将 lili 描述成 Bilibili 桌面客户端的任何文案。
- 首页中的用户动态、关注统计和 B 站行为数据。
- 与播放无关的社交信息流式展示。
- “歌曲/专辑/歌手全网搜索”等当前无法兑现的承诺。
- 私人 FM、每日推荐、猜你喜欢等算法型表述。
- 云同步、跨设备同步、本地标签编辑等未实现能力。

说明：这里的“删除”主要指从主导航和主要页面删除，不要求立即移除底层 service 或路由。第一阶段可以保留深层入口，待使用数据和稳定性验证后再决定是否删除代码。

## 8. 核心页面需求

### 8.1 发现音乐

#### 目标

让用户打开应用后，能够在最少操作内开始连续播放。

#### 页面结构

1. 顶部分类：音乐、流行、鬼畜。
2. 新歌速递：仅在“流行”分类展示，沿用现有接口。
3. 推荐内容列表/网格。
4. 播放全部。
5. 加载更多。

#### 单项操作

- 单击选中。
- 双击或点击播放按钮立即播放。
- 下一首播放。
- 添加到播放队列。
- 收藏。
- 下载音频。
- 更多：下载视频、打开 Bilibili。

#### 明确不包含

- 个性化推荐声明。
- 每日私人歌单。
- 猜你喜欢。
- 榜单名次预测或趋势数据。

### 8.2 我的收藏

#### 目标

将 Bilibili 收藏数据用音乐播放列表的方式呈现。

#### 页面结构

- 自建播放列表。
- 收藏的播放列表。
- 合集与系列。
- 最近打开的列表可在客户端本地排序，但不承诺云端同步排序。

#### 播放列表详情

- 封面、名称、创建者、数量和简介。
- 播放全部。
- 收藏/取消收藏。
- 音频批量下载。
- 内容列表。
- 更多：编辑、清理失效、视频下载、删除。

### 8.3 稍后播放

#### 目标

将 Bilibili 稍后再看转化为临时音乐收听清单。

#### 需求

- 保留与 Bilibili 稍后再看列表一致的数据。
- 支持播放全部、单项播放、搜索、删除。
- 页面附注“与 Bilibili 稍后再看同步”。
- 不改变服务端列表的业务含义。

### 8.4 本地音乐

#### 目标

让用户在同一播放器内收听本地文件。

#### 需求

- 添加/移除扫描目录。
- 刷新扫描。
- 搜索与排序。
- 显示标题、格式、大小、时长和创建时间。
- 播放全部、立即播放、加入队列。
- 删除本地文件前二次确认并明确不可恢复。

### 8.5 下载管理

#### 目标

集中管理由 lili 创建的音频和视频下载任务。

#### 需求

- 默认展示音频任务。
- 支持全部、音频、视频筛选。
- 支持暂停、继续、重试、删除。
- 显示下载、合并、转换等真实状态。
- 已完成任务可定位文件。
- 页面可打开下载目录。
- 视频下载入口保留，但在内容菜单的“更多”中。

### 8.6 搜索

#### 目标

快速找到可播放的 Bilibili 音乐内容和创作者。

#### 需求

- 搜索框文案为“搜索音乐视频或创作者”。
- 搜索建议与本地搜索历史。
- 结果 Tab：音乐视频、创作者。
- 音乐视频结果直接支持播放、下一首、入队、收藏和音频下载。
- 创作者结果进入创作者详情或直接关注。

### 8.7 播放栏

#### 永久可见信息

- 当前封面。
- 曲目标题。
- 创作者。
- 播放/暂停、上一首、下一首。
- 进度和时间。
- 音量。
- 播放队列。

#### 次级操作

- 收藏。
- 播放模式。

- 进入播放详情。
- Mini 模式。

#### 行为

- 空队列时显示清晰空状态，不展示无效控制。
- 播放失败时说明原因并允许重试，不自动跳过多个条目而无提示。

### 8.8 当前播放详情

#### 页面结构

- 封面区。
- 曲目信息。
- 同步歌词。
- 播放控制。

- 可选频谱。
- 一段时间无鼠标操作后弱化控制层。

### 8.9 我的关注与创作者

#### 目标

## 14. 验收标准

### 14.1 产品结构

- 一级固定导航不超过 5 个功能入口，不含用户播放列表。
- 首页不出现动态、关注统计、社交信息流或未实现的个性化推荐。
- 用户可从任意内容列表在两次操作内开始播放。
- 收藏夹、合集和系列采用一致的详情结构。

### 14.2 能力边界

- 所有可见按钮均能映射到现有 service、store 或 Electron API。
- 不出现“专辑、歌手曲库、私人 FM、每日推荐、云同步”等无法兑现的产品承诺。
- “B站历史”“稍后播放”等服务端数据来源表达清楚。

### 14.3 播放体验

- 播放栏在主窗口所有核心页面持续可见。
- 播放、暂停、上一首、下一首、进度、音量、模式和队列行为保持兼容。
- 在线视频音轨、Bilibili 音频和本地文件均可进入同一播放队列。
- 多分P内容顺序和随机播放规则不回归。

### 14.4 桌面体验

- 最低窗口尺寸下核心播放控制不可被遮挡。
- macOS、Windows、Linux 的窗口控制不回归。
- 应用内和全局快捷键继续有效。
- Mini 播放器、系统媒体控制、托盘和自动更新继续有效。

### 14.5 数据与操作安全

- 删除收藏夹、清空历史、删除本地文件和删除未完成下载任务均保留确认机制。
- 登录失效时不会丢失本地播放队列、设置和歌词缓存。
- 重构不改变既有 store 持久化字段含义，必要变更提供迁移逻辑。

## 15. 实施约束

1. 不修改现有 Bilibili API 的请求含义。
2. 不以 UI 需求倒逼新增未知服务端接口。
3. 页面重构优先建立 adapter，把收藏夹、合集和系列转换成统一的播放列表视图模型。
4. 播放 store、下载任务和 Electron IPC 先保持接口兼容。
5. 先迁移外壳和公共组件，再逐页迁移，避免长期存在同页两套视觉。
6. 任何“智能”“个性化”“同步”文案必须有真实数据能力支持。
7. 删除入口前先保留路由一版，验证用户仍能通过上下文入口访问相关能力。

## 16. 推荐版本范围

本 PRD 建议作为一次大版本重构实施：

- 产品名称：lili
- 版本定位：lili 2.0

- 数据兼容：保留现有登录态、收藏夹、播放队列、播放进度、设置、快捷键、下载记录和歌词缓存。
